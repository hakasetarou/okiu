# マップ＋番号検索の統合UI（C案）

## 1. 実装した内容

既存の「マップから探す」に番号検索を追加しました。場所から探す操作と番号を入力する操作を、同じマップで使える構成です。

- マップ上部に枠番号入力、位置表示ボタン、入力欄付近のエラーを配置
- 実際の登録番号と座標JSONを照合し、検索対象へ拡大・移動
- 青い外周と「検索対象」の文字で強調。空き・使用中・自分の枠の表示は維持
- 空きは「この駐車枠を選択」、自分の枠は「出庫手続き」から既存の処理へ進む
- 検索だけでは時刻入力・出庫確認を開始せず、書き込みAPIも呼ばない
- 二重検索、古い応答、マップ切り替え後の応答、ピンチ後の誤選択を防止
- 旧番号一覧・番号付き図面は保持し、統合マップの確認後に通常画面の入口だけを非表示にした

予約・GPS・経路案内・空き枠フィルターは追加していません。

## 2. 変更ファイル

- `public/map-search.js`：入力検証、登録番号・座標・状態の照合、検索用の位置計算

## 3. 番号と座標の対応

`lot.spaces[].id`に登録番号が存在することを確認し、座標JSONの`spot.id`へ対応付けます。収容台数以内という理由だけでは、有効な番号と判定しません。

入力は前後の空白と全角数字を整え、1以上の整数だけを受け付けます。空欄・0・負数・小数・文字混在・安全に扱えない大きな整数を拒否します。

- 登録番号にない場合：「第2駐車場に206番はありません」
- 登録番号はあるが座標がない場合：「100番は存在しますが、現在図面の位置を表示できません」
- 空き情報の取得失敗：入力不正とは別のメッセージを検索欄付近に表示

## 4. 検索対象への拡大・移動

既存マップのPanzoomをそのまま使います。新しいPanzoomやライブラリは追加していません。

周辺枠による既存の倍率計算に加え、検索対象の短辺・番号の文字サイズも参考にします。現在の倍率が十分ならその倍率を保ち、対象へ位置だけ移動します。既存の最大倍率は変更しません。

画像とSVGの共通の親要素を拡大・移動します。端では既存の移動範囲計算を使い、余白が出すぎない位置に補正します。結果パネルが表示された後の高さで再計算します。

青い外周は元の状態線より後ろに置きます。親要素の拡大で線が太くなりすぎないよう補正し、自分の黄枠の外側にも青を残します。全体表示・別番号の検索・駐車場切り替え・閉じる操作で解除します。

既存上限では図面上の文字が14pxに届かない場合があります。その場合も上限は増やさず、結果欄に番号を明記します。

## 5. 検索結果からの駐車・出庫

検索時には既存の`GET /api/parking/status`で空き情報を読み直します。自分の枠を優先して判定します。

| 状態 | 結果からの操作 |
|---|---|
| 空き | 「この駐車枠を選択」→既存の予定時刻入力 |
| 使用中 | 登録ボタンを隠し、取得できた出庫予定を表示 |
| 自分の枠 | 「出庫手続き」→既存の出庫確認 |

ボタンからは既存の`handleSpotCheckIn`を呼びます。最終的な登録・出庫は従来の共通処理とサーバー側チェックで行います。検索後に他の利用者が登録する場合も、既存の拒否応答を成功として扱いません。

検索結果の状態は取得時点の情報です。継続的な自動更新は今回の範囲外です。

## 6. 旧「番号から探す」の扱い

通常のカードから旧ボタンを非表示にし、コード・図面・番号一覧・処理・テストは保持します。`SHOW_LEGACY_NUMBER_ENTRY`を`true`に戻すと、入口を再表示できる構成です。

統合マップを4種類の画面寸法で検証した後に設定を切り替え、非表示にした最終版も再確認しました。通常画面では各駐車場の「マップから探す」だけが表示されます。

## 9. ブラウザ確認

**実Edgeを画面を表示しない方式（ヘッドレス）で自動操作し、全ケース成功しました。** 実際のPanzoom 4.5.1と、架空の利用者・駐車状態を使いました。確認用サーバーは127.0.0.1だけで待ち受け、実DBには接続していません。

```powershell
node tests/helpers/integrated-map-browser-check.cjs "$env:TEMP\kari-autozoom-browser\panzoom-4.5.1.min.js" "$env:TEMP\kari-map-search-baseline-20261112" --expect-hidden
```

第1引数は、アプリが既に使う同じPanzoom 4.5.1の一時保存ファイルです。第2引数の変更前ファイルは省略できます。

確認寸法は393×852、360×800、852×393、1366×768pxです。各寸法で全6駐車場（計24組）を確認し、初回タップ・検索・拡大済みの位置移動・強調解除・ボタン・ホイール・合成2本指操作の確認に成功しました。第1は265番、第2は100番、第3は128番、第4は39番、第5は31番、第7は52番などを使用しました。

Enterはブラウザのキー入力で検索しました。表示領域の高さ変更と回転もブラウザで発生させ、検索結果の保持と位置の再計算を確認しました。入力欄に操作中は結果パネルを一時的に折りたたみ、地図操作ボタンを横並びにして領域を確保します。

検索結果から時刻入力・キャンセル・登録・出庫確認・キャンセル・出庫まで確認しました。また、試験用APIの409拒否応答で成功扱いしないこと、旧番号一覧の内部処理が引き続き動くことも確認しました。

通信失敗、存在しない番号、存在するが座標がない番号、古い応答の破棄も確認済みです。検索だけでは登録・出庫への書き込み要求が出ず、明示的な操作をしたテストだけが試験用APIへ書き込みました。これは実DBの書き込み確認ではありません。

## 11. 残る課題・改善候補

確認した範囲では未解決の機能不具合はありません。

既存の最大倍率では、特に狭い横向き画面で図面上の番号文字が小さい場合があります。852×393pxの第4・第5駐車場の確認番号は約11.7px、第2の100番は360×800pxで約12.2pxでした。第3の128番は4寸法とも約18.6〜18.9pxでした。番号を結果欄にも表示し、倍率上限は維持しています。図面全体の文字の描き方は変更していません。

利用者評価後に、旧番号一覧を再表示する必要性や検索結果カードの大きさを判断します。

## 12. 卒論進捗発表用の要約

改善前は「番号一覧」と「マップ」に入口が分かれ、番号を直接指定してマップへ移動できませんでした。改善後は1つのマップで場所から探す操作を維持しつつ、番号入力で該当枠へ移動・強調し、状態を確認して明示的に選択できます。

操作時間の短縮は、まだ実測していないため断定しません。第3駐車場128番など同じ課題・画面寸法・空き状況で、発見時間、タップ数、誤操作数、5段階の分かりやすさを比較する計画です。
